# 2026-10-20: native TCP session reuse

## Outcome and activation boundary

Added opt-in native smux on the existing VLESS/REALITY Vision transport. The
owned Seoul node now explicitly accepts multiplex requests on TCP/443, while
retaining its existing Vision user and HY2 service. The active local server
entry has `reality_multiplex: true`. Its generated client config passes the
installed sing-box 1.14.3 checker with authenticated TLS, Vision, and an 8/1 pool.

The running root-owned local daemon still uses its original non-multiplexed
config. The verified replacement is built as `./mole`; install and reconnect:

```sh
sudo install -m 755 ./mole /usr/local/bin/mole && mole down && mole up
```

Run this from the normal user's shell in this repository. `mole up` performs
its own elevation and preserves its normal lid-destroy/key setup. Passwordless
sudo was unavailable in the investigation terminal, so activation is pending.
The original `auto` transport mode and 400 Mbps ceiling were restored.

## Evidence and mechanism

The local log snapshot from 10:36:01 to 15:38:00 contained 125 `i/o timeout`
strings, 20 slow fresh-dial records, and two failed fresh-dial records, with no
ENOBUFS, fallback, or local-link latch records. Many connection errors explicitly
named the dial to the VPS's TCP/443 socket, including ChatGPT requests. Warm
flows and bulk transfers continued working. This locates those failures before
the destination-site connection; it does not identify the equipment or policy
dropping the packets. The supervisor's sparse sample does not capture every
application failure.

The node had negligible CPU load, about 565 MiB available RAM, no NIC error/drop
counters, and TCP paths with roughly 103–114 ms minimum RTT in the inspected
sockets. Brutal pacing was active at 400 Mbps. These are point observations,
not proof of capacity under every workload.

`config/parser.go` previously categorically blamed Vision for broken h2mux
sessions. The generated node config did not explicitly enable multiplex.
The server journal instead showed the deprecated-global-multiplex rejection
when probed with Vision + mux, and a flow mismatch when Vision was omitted.
An isolated server with an explicitly enabled inbound carried both Vision +
smux and a separate non-Vision test identity. The subsequent TCP/443 experiment
used the original Vision identity on both candidates. No new protocol, port,
credential, TLS bypass, or transport-selection algorithm is required.

Native session reuse avoids a new outer TCP/REALITY handshake for every
application flow once the pool is warm. It cannot eliminate initial cold-pool
dials, shared TCP loss, node egress delays, or Wi-Fi limits.

## Same-node comparison

Both candidates used the same IP, TCP/443, credentials, endpoint, and 400 Mbps
pacing. Fresh HTTPS requests validated certificates and status, disabled
application connection reuse, alternated the submission order, and sampled
Cloudflare trace plus Google's connectivity endpoint. Each bulk phase received
at most 128 MiB for at most ten seconds plus socket cleanup, with equal
application concurrency; new ENOBUFS would stop the experiment.

| Native pool | Measurement | Original Vision | Vision + smux |
| --- | --- | --- | --- |
| 8 connections / expand after 1 active stream | Fresh HTTPS, success | 23/24 | 24/24 |
| same | Successful HTTPS median | 620 ms | 402 ms |
| same, first order | One-flow payload download | 45.9 Mbps | 99.6 Mbps |
| same, reversed order | One-flow payload download | 52.2 Mbps | 129.5 Mbps |
| same, first order | Eight-flow payload download | 235.9 Mbps | 236.5 Mbps |
| same, reversed order | Eight-flow payload download | 258.3 Mbps | 318.8 Mbps |

All these bulk phases completed without request errors or new ENOBUFS. The
failed plain HTTPS request remains in the raw evidence and is excluded from
the successful-request median, rather than represented as a fast zero.

The first 4/4 pool reduced setup latency and improved one-flow download, but
eight-flow results fell to 212.8–238.0 Mbps against 253.6–254.6 Mbps on the
original. That pool was rejected. The 8/1 native setting lets concurrent bulk
flows expand while preserving reuse across sequential requests.

These short sequential phases include startup and stop early when their byte
budget is used. They measure owned-node-to-client payload through fixed
loopback forwarders, bypassing the client's TUN packet-processing path. They
do not establish sustained capacity, website download/upload speed, a stable
percentage gain, or the result after local daemon activation. The 318.8 Mbps
sample is a short observed result, not a promised new ceiling.

Raw timings, failures, byte counts, elapsed intervals, and rejected-pool results:
[measurements](2026-10-20-measurements.jsonl).

## Implementation and verification

- `mux=smux` and the stored boolean opt in explicitly; older server records
  retain the original URI and client behavior. Unsupported mux names fail.
- Generated node configs explicitly support multiplex and preserve the
  original Vision identity. Client opt-in remains separate from this capability.
- A real-engine regression sends eight fresh application flows through
  authenticated TLS + Vision + smux and verifies body delivery and outer
  connection reuse. Unit constraints cover URI/storage/import and node config.
- `scripts/measure-dual.py` now holds total concurrency constant across TCP,
  HY2, and both; its previous 4/4/8 comparison could overstate dual-route gains.
  A CLI regression reproduces that mismatch before the fix.
- Final gate: `bash scripts/verify-performance.sh /tmp/mole-performance-20261020`
  passed Go race tests, three Python tests, and the macOS build. The generated
  active-node client and server configs passed `sing-box check`.
- Built binary SHA256:
  `539b36826e6de38c79f7f5ddb4d6ec04058de51f2929964a829661b470175bcd`.
