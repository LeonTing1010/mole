# Mole 优化执行与验收 — 2026-11-05

## 已生效的结果

本机控制器与当前 VPS 已更新。明确测得的收益是新外层连接建立更快：服务端启用 TCP Fast Open 后，同一轮交替对照中，关闭客户端 TFO 的 TLS 就绪中位数为 341.7 ms，开启为 230.1 ms，减少 111.7 ms（约 32.7%）。每组 30 次，均成功返回 HTTP 200。

最终保留 REALITY + Vision + smux 8/1 主用、TCP Brutal 600 Mbps，HY2 400 Mbps 备用，gVisor / MTU 9000。没有升级 VPS、切换到双路或扩大缓冲。队列保留当前 fq_codel，并将部署默认值同步为 fq_codel；不再把尚未通过验收的 fq 当成目标。

这里的收益限于新的外层 TCP/TLS 会话。热复用连接没有这次握手可省，数据不代表模型首 token 或生成速度。持续下载没有经过匹配对照证明相对此前整体提速。

## TFO 的对照与实际生效证据

服务端关闭 TFO 时，客户端关闭/开启的 TLS 中位数分别约 340.4 / 338.7 ms；服务端开启后，对照为 341.7 / 230.1 ms。前后各 60 个请求，共 120 个，全部成功。

请求使用独立、无 multiplex 的外层连接，开启/关闭客户端 TFO 的顺序交替。没有清空操作系统 cookie 缓存，不能把全部请求称为 cold-cookie 测试；没有测量每个 SYN 的到达时间。VPS FastOpenPassive 计数从 2 增至 39，FastOpenPassiveFail 没有增加，补足了“只有配置 true”的证据缺口。

服务端修改保留原认证身份，配置检查通过，使用 HY2 管理通道完成更新，并预设自动回退。双协议认证和后续请求通过后取消回退定时器。

## 速率扫描：保留 600 Mbps

固定 fq_codel，每个目标做五轮，共 20 段；每轮八条应用连接。最多 1 GiB payload，20 秒后停止新请求并读完在途响应。500/600 的样本在约 16–19 秒提前收齐预算，均属于短样本；300/400 达到 20 秒。

| 目标 Mbps | 实收中位数 Mbps | 新 HTTPS TTFB 中位数 ms | 成功样本 p95 ms | HTTPS 探测失败/总数 |
|---:|---:|---:|---:|---:|
| 300 | 296.9 | 439 | 2641 | 3/71 |
| 400 | 396.0 | 455 | 2102 | 0/72 |
| 500 | 488.5 | 610 | 1862 | 0/64 |
| 600 | 521.3 | 688 | 1551 | 0/58 |

所有 bulk 请求完成，无新增客户端 ENOBUFS。300 的三次 HTTPS 失败包括两次超时及一次 TLS 错误，未被算作零延迟，也未进入成功样本分位数。500 没有显示更好的尾延迟，600 保留更高吞吐，因此没有降低或提高生产目标。

这些是节点 loopback keeper 到客户端的固定转发测量，绕过应用到 TUN 的入站处理。新建 HTTPS 探测与 bulk 共用主隧道，不能代表已有浏览器 HTTP/2 会话。各轮按固定升序扫描，有时间/顺序影响；没有用它声称全局最优或长期容量。500+ Mbps 也不能与此前不同时段短测相除，宣称修复使下载翻倍。

VPS 这 20 个观测窗口的 CPU 平均占用中位数约 17.5%、最高约 22.1%。窗口包括边界采集时间，不能当作峰值；没有支持立即升级机器的证据。

## fq、并发池和压力测试边界

fq 的队列矩阵没有完成计划中的五对验收。两批测试共遇到四次带前导零字节的 HTTP 状态行错误，一批在 fq_codel / 16 连接，另一批在 fq / 8 连接。后者在不主动截断响应的测量方式中仍出现，因此不能认定“读完响应”已解决它，也不能认定 fq 是起因。两批均停止，原队列和速率已恢复；失败证据保留。

隔离引擎的无 mux、smux4、smux8、smux16，各三轮、每轮 64 MiB、16 应用连接均完成，没有复现格式错误。生产引擎另一次 256 MiB / 16 连接完整传输也通过。冷/热差异与样本波动明显，没有足够证据扩大连接池。

协议状态字节与前导零现象值得继续调查，但本次没有包级定位或确定性回归用例，不能宣布其根因已经修复。重新启动引擎后完成的速率扫描不能抹去此前失败。

首个队列控制器原地重复指定 flows 被 Linux 拒绝，未产生有效测速；改为同算法不重建、跨算法才创建后，恢复路径实际演练通过。此工具错误的记录独立保留。

## 上传：发现限制，没有宣称改善

所有成功上传都检查了服务端实际接收字节与 SHA-256。固定转发 REALITY 三轮中位数约 161.7 Mbps，HY2 约 4.8 Mbps。降低独立 HY2 客户端上传声明至 64/128/256 Mbps，各两次 8 MiB 测量仍约 4.8–5.3 Mbps，没有采用新值。

生产 TUN 的 localhost/FakeIP 路径，16 MiB 样本约 10.2 Mbps；另一次 16 MiB 尝试未取得有效响应，保留失败。后续 4 MiB 完整传输约 1.6 Mbps，实际连接链为 `flow-7 → proxy → proxy-reality`，排除了误切 HY2。最终重连后的另一个 4 MiB 样本约 4.8 Mbps。

隔离 TUN 使用独立 FakeIP 范围、自己的接口和单地址路由；不改系统默认路由或 DNS。gVisor MTU 9000 的两次 4 MiB 上传约 16.5 / 26.0 Mbps，MTU 1500 为 16.9 / 26.1 Mbps，未显示有意义的收益。system / mixed 都未通过隔离 HTTPS pilot，未进入性能比较，更未升级生产。测试接口全部删除，系统 DNS、默认路由及生产配置哈希前后保持一致。

上述路径的会话年龄、工作负载和预算不同，不能用相除所得比例认定 gVisor 开销。上传限制的具体机制尚未定位；也未证明是 ISP 限速、VPS CPU、窗口、MTU或单一软件缺陷。保持原配置，避免凭下载结果推断上传已经优化。

上传工具还遇到一次 BrokenPipe、短时服务过期及一处启动脚本缩进错误；这些不是成功样本，未当作零速率。修正后才得到带字节/哈希确认的结果。

## IPv6 与最终验收

安装版 1.14.4 的 direct dialer 会进行并行地址回退。VPS 上以不可达文档 IPv6 地址和正常 IPv4 loopback 源站构造隔离配置，五次请求均回退成功，约 315 ms。此用例不证明所有 IPv6 故障模式，但否定了沿用旧注释认定当前版本永不回退。保持原 IPv6 优先出口。

最终安装产物通过全部 Go race 测试、六项 Python 测试、构建、go vet 和 diff 检查。最终控制器切换验收包括：生成配置一致、实际直连/FakeIP DNS、9 次 HTTPS、64 MiB 完整 TUN 下载、PF 状态与实际节点豁免、合盖销毁 armed、600 Mbps pacing confirmed。上传测试后再做 9 次 HTTPS，均通过。

普通用户的最后一次 verify 因 PF 提权超时，未进入协议探测；失败回执另存。管理员上下文重跑时首轮两协议 HTTPS 尝试失败，下一轮分别成功，最终协议与调优状态均为 ready。没有把首次失败改写为全部尝试成功。
